## 1. Что должен делать Backend-агент

Backend-агент — **единственный агент, который пишет Python-код**. Он берёт задачу из плана и выдаёт готовый, рабочий код.

| Делает | Не делает |
|--------|-----------|
| Пишет `models.py`, `views.py`, `forms.py`, `admin.py`, `services.py` | Не проектирует архитектуру (это Архитектор) |
| Создаёт миграции (`makemigrations`) | Не разбивает на задачи (это Планировщик) |
| Пишет тесты (`pytest-django`) | Не решает, какие фичи нужны (это пользователь) |
| Настраивает `settings.py` (частично) | Не пишет HTML/CSS/JS (это Frontend-агент) |
| Пишет `urls.py`, `serializers.py` (если DRF) | Не настраивает Docker/nginx (это DevOps-агент) |
| Рефакторит существующий код по ТЗ | Не сканирует проект (это Scanner) |

**Ключевое правило:** Backend-агент работает **только по спецификации**. Если в плане написано «создать модель Subscription с полями user, plan, status» — он создаёт именно это. Если он видит, что план противоречит существующему коду — он флагает проблему, но не меняет архитектуру сам.

## 2. Какие данные получает

Backend-агент получает **одну конкретную задачу** из плана + контекст:

| Источник | Что именно | Зачем |
|----------|-----------|-------|
| **Планировщик** | Строка из таблицы задач (например, «1.1 Create Subscription model») | Понимает, что делать |
| **Архитектор** | ERD, API-контракт, ADR (если нужно) | Понимает, как связано с остальным |
| **AS-IS** (опционально) | Текущий `models.py`, `views.py` | Понимает, что уже есть, чтобы не сломать |
| **Пользователь** | Уточнения, если агент задаёт вопросы | Разрешает неоднозначности |

**Формат входа:**
```markdown
## Task 1.1: Create Subscription model
**Agent**: Backend
**Input**: ADR-002, ERD v1.1
**Output**: `apps/billing/models.py` + migration
**Acceptance Criteria**:
  - Миграция применяется
  - Модель видна в admin
  - Поля: user (FK → users.User), plan (CharField: basic/pro),
    status (CharField: active/cancelled/expired), expires_at (DateTimeField)
**Depends On**: — (нет зависимостей)
**MVP**: Yes

## Context
### Current models.py (AS-IS)
```python
# apps/billing/models.py — пустой файл
```

### ERD (relevant part)
```
Subscription
├── user: FK → User
├── plan: CharField(choices=[basic, pro])
├── status: CharField(choices=[active, cancelled, expired])
├── expires_at: DateTimeField
├── created_at: DateTimeField(auto_now_add)
```

### ADR-002 (relevant part)
Используем Fat Model. Логика проверки срока — в методе `is_expired()`.
```


## 3. Понимает ли агент, что это Django?

**Да, должен понимать.** И вот почему это критично:

| Если агент НЕ знает Django | Если агент ЗНАЕТ Django |
|---------------------------|------------------------|
| Напишет `class User(BaseModel)` вместо `AbstractUser` | Использует `from django.contrib.auth.models import AbstractUser` |
| Создаст REST API на чистом Python | Использует `from django.views.generic import ListView` или DRF |
| Напишет SQL-запросы руками | Использует ORM: `Post.objects.select_related('author')` |
| Забудет про `makemigrations` | Автоматически добавляет `makemigrations` в выход |
| Не поймёт, где settings | Знает про `DJANGO_SETTINGS_MODULE` и split-settings |

**Но:** Агент не должен быть «зашит» только под Django. Лучше сделать **Django-специфичный Backend-агент** с явным указанием стека в промпте. Если в будущем понадобится FastAPI — создадите другого агента.


## Как Backend-агент вписывается в пайплайн

```
Пользователь
    ▼
[Planner] → выдаёт plan_v1.1.md
    ▼
Пользователь выбирает задачу 1.1 (или batch: 1.1-1.3)
    ▼
[Backend Agent] ← получает Task 1.1 + ERD + AS-IS
    ├─ Пишет models.py
    ├─ Пишет tests.py
    ├─ Генерирует миграцию (описывает)
    └─ Пишет admin.py
    ▼
Пользователь проверяет, применяет миграции, запускает тесты
    ▼
[Frontend Agent] ← получает Task 2.3 (шаблоны)
    ▼
[QA / Review] ← проверяет соответствие архитектуре
```
