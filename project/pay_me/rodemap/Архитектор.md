


# Архитектор
- это проектировщик системы, а не строитель.
    - Его задача — превратить бизнес-требования в четкую техническую спецификацию, по которой другие агенты будут писать код.
| Артефакт                      | Пример                                                           |
| ----------------------------- | ---------------------------------------------------------------- |
**Структура проекта**         | Какие Django-apps, папки, модули                                 |
**ERD / Модели данных**       | Поля, связи, индексы, constraints                                |
**API-контракты**             | Endpoints, методы, request/response JSON Schema                  |
**Потоки данных**             | Как запрос проходит через middleware → view → service → ORM → БД |
**ADR**                       | Почему выбран Django Templates, а не DRF + React                 |
**Интерфейсы между агентами** | Что ожидает Backend-агент от Frontend-агента                     |


Если Архитектор начнет писать код
- он превращается в разработчика, и вы теряете слой абстракции, который защищает проект от хаотичных решений.



# Практический пример пайплайна для вашего стека
Пользователь: "Сделай блог на Django 5.2"
    ↓
[Архитектор]
  → Структура: apps/blog, apps/users, apps/comments
  → ERD: Post, User, Comment, Tag
  → API: /api/posts/ (GET, POST), /api/posts/<id>/comments/ (GET, POST)
  → ADR: "Используем Django Templates + HTMX, т.к. SEO важен"
  → Контракт: Frontend-агент делает templates/, Backend-агент делает views.py и models.py
    ↓
[Планировщик]
  → Задача 1: Backend-агент — модели + миграции
  → Задача 2: Backend-агент — views + urls
  → Задача 3: Frontend-агент — base.html + post_list.html + HTMX
  → Задача 4: DevOps-агент — Docker + docker-compose
    ↓
[Агенты-параллельно] (Backend и Frontend могут работать одновременно,
                       т.к. у них четкие контракты от Архитектора)


| Фаза              | Когда вызывать                       | Что делает Архитектор                                       |
| ----------------- | ------------------------------------ | ----------------------------------------------------------- |
| **Старт проекта** | Перед первой строкой кода            | Полная архитектура: структура, модели, API, ADR             |
| **Новая фича**    | Перед реализацией фичи               | Дополнение архитектуры: новые модели, endpoints, интеграции |
| **Рефакторинг**   | Когда текущая архитектура «ломается» | Пересмотр границ apps, выделение сервисов, миграция данных  |




# Чего НЕ делать:
1. Не вызывайте Архитектора на каждый багфикс или CSS-правку — это тормозит Vibe Coding.
Не заставляйте его «одобрять» каждый PR — это анализ паралича.


2. Скан проекта: Архитектор НЕ должен сканировать сам
Архитектор — проектировщик, а не файловый менеджер. Давать ему задачу «просканируй папки» — это нарушение Single Responsibility.

[Code Scanner / File Analyzer] — под-агент
    ↓
Читает файлы проекта → Создает сводку (AS-IS summary)
    ↓
[Architect] получает сводку + запрос пользователя → Проектирует TO-BE
    ↓
[Planner] разбивает TO-BE на задачи
    ↓
[Backend / Frontend / DevOps агенты] — исполняют

Что делает Code Scanner:
Список Django-apps и их моделей
URL-конфигурация
Зависимости (requirements.txt, pyproject.toml)
Ключевые сервисы/утилиты
Размер кодовой базы (строки, сложность)
Текущие ADR (если есть)

Формат выхода Code Scanner: Markdown-таблица или JSON — чтобы Архитектор быстро прочитал контекст.

Итоговый чеклист
[ ] Code Scanner — отдельный под-агент, не смешивать с Архитектором
[ ] Архитектор универсальный, но с Scope Rule — не лезть за пределы задачи
[ ] Вызывать на старте, при новых фичах и рефакторинге — не на каждый коммит
[ ] Передавать AS-IS контекст через файл, а не заставляя Архитектора сканировать
[ ] Архитектор → Планировщик → Разработчики — строгая цепочка, без пропусков




🔧 Что можно изменить или добавить:
Дополнительные артефакты:
- Sequence Diagrams — для сложных бизнес-процессов
- Security Checklist — аудит безопасности
- Performance Notes — где нужны индексы, кэширование
- Testing Strategy — что и как тестировать
- Deployment Guide — шаги деплоя
Для конкретных задач:
- Integration Patterns — как интегрироваться с внешними API
- Authentication Flow — схема авторизации/аутентификации
- Event-Driven Design — если нужны события (webhooks, signals)
- Caching Strategy — что и как кэшировать
