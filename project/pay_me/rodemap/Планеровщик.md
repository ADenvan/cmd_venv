User: Двигаться к Планировщику.
Архитектора получает сводку + запрос пользователя → Проектирует TO-BE
Что получает Планировщику ?
Давай разберемся что должен делать планировщик:
1. будет определять сложность задачи.
2. если задача сложная Разбивать на этапы.
3. Он мог определять и составить минимум MVP для реализации.
4. Если задача небольшая разбить на подзадачи и передать готовы план.

Поведение планировщика:
Должен ли планировщик сохранить фаил плана если план сложный и много этапов задач или это избыточно?

Kimi: Разберём Планировщика по полочкам — что ему дают, что он делает и как выдаёт результат.

---

## 1. Что получает Планировщик на вход

Планировщик работает **только после Архитектора**. На вход он получает:

| Источник | Что именно |
|----------|------------|
| **Архитектор** | Все артефакты: структура проекта, модели, API-контракты, ADR, Data Flow |
| **Пользователь** | Контекст приоритетов: «сначала авторизация», «MVP за неделю», «отложить комментарии» |
| **AS-IS (опционально)** | Текущее состояние проекта (от Scanner), если это не проект с нуля |

**Важно:** Планировщик НЕ получает исходный код. Только архитектурные артефакты.

## 2. Что должен делать Планировщик

### 2.1 Определять сложность задачи

Планировщик оценивает каждую часть архитектуры по шкале:

| Уровень | Критерии | Пример |
|---------|----------|--------|
| **Simple** | 1 модель, 1-2 views, шаблон, без внешних API | Страница «О нас» |
| **Medium** | 2-3 модели со связями, CRUD, формы, валидация | Система тегов к постам |
| **Complex** | Кастомная логика, интеграции, async, изменения в нескольких apps | Платежи через Stripe + Webhooks |
| **Architectural** | Меняет границы apps, требует миграции данных, влияет на всю систему | Вынос авторизации в отдельный микросервис |

### 2.2 Разбивать сложные задачи на этапы

Если Архитектор спроектировал фичу уровня **Complex**, Планировщик делит её на этапы:

```
Этап 1: Модели + миграции (без бизнес-логики)
Этап 2: API / Views (без интеграций)
Этап 3: Интеграция внешнего сервиса (Stripe)
Этап 4: Frontend + HTMX
Этап 5: Тесты + полировка
```

**Правило:** Каждый этап должен оставлять проект в рабочем состоянии (не ломать билд).

### 2.3 Составлять MVP

Планировщик выделяет **минимальный набор задач**, при котором фича работает «в рамках happy path»:

| Полная фича | MVP-версия |
|-------------|------------|
| Комментарии с лайками, дизлайками, вложениями | Только текстовые комментарии без лайков |
| Платежи с подписками, пробным периодом, купонами | Одиночная покупка, без подписок |
| Чат с WebSocket, файлами, статусами | Только отправка текста, без статусов «прочитано» |

**MVP-флаг:** Каждая задача помечается `[MVP]` или `[Post-MVP]`.

### 2.4 Разбивать на подзадачи для агентов

Каждый этап превращается в **конкретные задачи** для конкретных агентов:

```markdown
### Задача 1.1: Backend — Модель Subscription
**Агент**: Backend Developer
**Вход**: ADR-002, ERD v1.1
**Выход**: `apps/billing/models.py` с моделью Subscription + миграция
**Критерий готовности**: Миграция применяется, модель видна в admin
**Зависимости**: Нет
**Оценка**: Simple (30 мин)
```

## 3. Должен ли Планировщик сохранять файл плана?

**Да, обязательно.** И вот почему:

| Причина | Почему это важно |
|---------|------------------|
| **Агенты работают параллельно** | Backend и Frontend агенты берут задачи из одного файла |
| **Версионирование** | `plan_v1.0.md` → `plan_v1.1.md`. Видно, что изменилось |
| **Отслеживание прогресса** | Вычёркиваете выполненные задачи, не теряя контекст |
| **Повторный вход** | Если сессия прервалась, вы не начинаете планирование с нуля |

**Но** — файл должен быть **компактным**, не 10 страниц:

- Для **Simple** задачи: 5-10 пунктов, одна секция.
- Для **Complex** проекта: 3-5 этапов, каждый 5-8 задач. Итого 1-2 страницы.

## 4. Промпт для Планировщика

```markdown
# System Prompt: Task Planner (Django Vibe Coding)

## Role
You are a Task Planner for a solo developer using CLI agents. You receive architecture artifacts from the Architect and break them into actionable, prioritized tasks for implementation agents.

## Input
You will receive:
1. Architecture artifacts (structure, models, API, ADR, data flow)
2. AS-IS report (if project exists)
3. User context (deadlines, priorities, constraints)

## Output: Implementation Plan
Produce a single Markdown file: `plan_v[X.Y].md` where X.Y matches the architecture version.

### Structure:
```markdown
# Implementation Plan v[X.Y]
**Architecture Version**: v[X.Y]
**Date**: YYYY-MM-DD
**Complexity**: [Simple / Medium / Complex / Architectural]
**Estimated Total Time**: [N hours]

---

## Phase 1: Foundation
**Goal**: [What works after this phase]

| # | Task | Agent | Input | Output | Acceptance Criteria | Depends On | MVP? | Est. Time |
|---|------|-------|-------|--------|---------------------|------------|------|-----------|
| 1.1 | Create Subscription model | Backend | ADR-002, ERD | models.py + migration | Migration applies, admin works | — | Yes | 30m |
| 1.2 | Create PaymentForm | Backend | API contract | forms.py | Form validates amount > 0 | 1.1 | Yes | 20m |

## Phase 2: Core Logic
...

## Phase 3: Integration
...

## Phase 4: Frontend & Polish
...

---

## MVP Scope
[List of tasks marked MVP — minimum to ship]

## Post-MVP / Nice to Have
[List of deferred tasks]

## Parallelization Map
[Which tasks can run simultaneously]
- Backend 1.1 + Frontend 4.1 (no dependency)
- Backend 2.2 depends on Backend 2.1
```

## Rules
1. **Every task must be atomic** — one agent, one file or one app, one clear output.
2. **Every task must have acceptance criteria** — how to know it's done.
3. **Mark MVP explicitly** — user should be able to stop after MVP and have working software.
4. **Respect dependencies** — never schedule a task before its dependencies.
5. **Estimate time** — rough (15m / 30m / 1h / 2h / 4h). Use 4h max per task; split larger ones.
6. **No code in plan** — only file names, function names, and requirements.
7. **Version sync** — plan version MUST match architecture version.
8. **If Simple task** (1 model + 2 views): skip phases, use flat task list.

## Complexity Assessment
Before planning, assess overall complexity:
- **Simple**: ≤ 2 models, ≤ 3 views, no external APIs, no auth changes.
- **Medium**: 2-4 models, CRUD, forms, templates, minor auth changes.
- **Complex**: Custom business logic, external API integration, async tasks, file uploads.
- **Architectural**: Changes app boundaries, database schema refactoring, auth system replacement.

## Task Sizing
- If a task takes > 4 hours → split into sub-tasks.
- If a task is < 15 minutes → merge with adjacent task.
- Aim for 30-90 minutes per task — optimal for vibe coding flow.

## Agent Types
- **Backend**: Django models, views, forms, admin, services, management commands.
- **Frontend**: Django templates, HTMX, Alpine.js, CSS, static files.
- **DevOps**: Docker, settings, env, CI/CD, nginx.
- **QA**: Tests, edge cases, fixtures.

## Forbidden
- ❌ Do not write Python code, SQL, or HTML.
- ❌ Do not create architecture — only decompose existing architecture.
- ❌ Do not skip MVP analysis.
- ❌ Do not create tasks without acceptance criteria.
```

## 5. Пример работы Планировщика

### Вход (от Архитектора):
```markdown
## Архитектура v1.1: Система подписок
- Модель Subscription (user FK, plan, status, expires_at)
- Интеграция Stripe (checkout session, webhook)
- Celery-таска для проверки просроченных подписок
- Шаблоны: страница выбора плана, страница успеха
- API: POST /billing/subscribe/, POST /billing/webhook/
```

### Выход (plan_v1.1.md):
```markdown
# Implementation Plan v1.1
**Architecture Version**: v1.1
**Date**: 2026-04-27
**Complexity**: Complex
**Estimated Total Time**: 8 hours

---

## Phase 1: Foundation (MVP)
**Goal**: Модель и админка работают. Можно создать подписку вручную.

| # | Task | Agent | Input | Output | Acceptance Criteria | Depends On | MVP? | Est. |
|---|------|-------|-------|--------|---------------------|------------|------|------|
| 1.1 | Модель Subscription + миграция | Backend | ERD v1.1 | `billing/models.py`, migration | Миграция применяется, видна в admin | — | Yes | 30m |
| 1.2 | Настройка Stripe keys в env | DevOps | ADR-003 | `.env.example`, `settings/base.py` | `django-environ` читает `STRIPE_SECRET_KEY` | — | Yes | 15m |
| 1.3 | Сервисный слой billing/services.py | Backend | ADR-003 | `services.py` с create_subscription() | Функция создает запись в БД | 1.1 | Yes | 45m |

## Phase 2: Stripe Integration (MVP)
**Goal**: Пользователь может оплатить подписку.

| # | Task | Agent | Input | Output | Acceptance Criteria | Depends On | MVP? | Est. |
|---|------|-------|-------|--------|---------------------|------------|------|------|
| 2.1 | Checkout Session view | Backend | API contract | `billing/views.py` | POST возвращает Stripe URL | 1.3, 1.2 | Yes | 1h |
| 2.2 | Webhook handler | Backend | API contract | `billing/webhooks.py` | Обрабатывает `checkout.completed` | 2.1 | Yes | 1h |
| 2.3 | Шаблон выбора плана | Frontend | Wireframe (описанный) | `templates/billing/plans.html` | Кнопка «Оформить» ведет на checkout | — | Yes | 45m |

## Phase 3: Async & Polish (Post-MVP)
**Goal**: Автоматическая проверка и уведомления.

| # | Task | Agent | Input | Output | Acceptance Criteria | Depends On | MVP? | Est. |
|---|------|-------|-------|--------|---------------------|------------|------|------|
| 3.1 | Celery-таска check_expired | Backend | ADR-003 | `billing/tasks.py` | Таска меняет status на expired | 1.1 | No | 45m |
| 3.2 | Шаблон страницы успеха | Frontend | — | `templates/billing/success.html` | Показывает статус подписки | 2.2 | No | 30m |
| 3.3 | Тесты на webhook | QA | Plan | `billing/tests.py` | Mock Stripe webhook проходит | 2.2 | No | 1h |

---

## MVP Scope
Задачи: 1.1, 1.2, 1.3, 2.1, 2.2, 2.3
**Результат MVP**: Пользователь выбирает план → платит через Stripe → подписка активна.

## Parallelization Map
- 1.1 и 1.2 — параллельно
- 1.3 зависит от 1.1
- 2.1 зависит от 1.3 и 1.2
- 2.3 можно делать параллельно с 2.1 (только шаблон, без логики)
```

## Итог

| Вопрос | Ответ |
|--------|-------|
| **Что получает Планировщик?** | Артефакты Архитектора + приоритеты пользователя |
| **Что делает?** | Оценивает сложность, делит на этапы, выделяет MVP, режет на атомарные задачи |
| **Сохранять файл плана?** | **Да.** `plan_v1.1.md` — это контракт между вами и агентами-исполнителями |
| **Когда НЕ сохранять?** | Только для тривиальных задач (1 view, 1 шаблон). Но даже тогда 5 строк в плане не помешают |
